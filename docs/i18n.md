# Internationalization (i18n)

How CHOIR speaks more than one language, where the strings live, and the
rules that keep translations honest. Supported today: `en` (source of truth)
and `ko`.

There are two independent settings, because a team can want CHOIR speaking
Korean in Slack while the repository stays English:

| Setting | What it governs | Where it is set |
|---|---|---|
| **UI language** | CHOIR's own words: Slack blocks, modals, ephemerals, DMs, the web viewer | per user (App Home → *Your language*, or the viewer's ⚙ Settings), falling back to the Slack profile locale, then the workspace default (App Home → *Language*, or the viewer's Settings; managers) |
| **Content language** | what CHOIR *writes into documents*: extracted knowledge, new sections, merged edits, image captions, the Google Docs banner | workspace-wide (App Home → *Document content language*, or the viewer's Settings; managers). `Follow the conversation` is the default and today's behaviour |

LLM answers in Slack are not covered by either: `qa-service` already answers
in the asker's language, and that stays a prompt rule.

## Resolving a locale

`services/i18n/resolve-locale.ts` — precedence, highest first:

1. `WorkspaceConfig.userLanguages[userId]` (explicit choice; `auto` clears it)
2. the Slack profile locale, from `users.info({ include_locale: true })`,
   cached alongside the display name in `services/common/name-cache.ts`
   (7 days, on disk). Slack sends locale on **no other payload**, so this is
   the only source.
3. `WorkspaceConfig.uiLanguage` (workspace default)
4. `en`

`app.ts` installs `localeMiddleware` right after the usage monitor; it stamps
the cached result on Bolt's `context.locale` without a network call.
`GET /api/docs/session` returns `language` using the same chain, with
`Accept-Language` slotted between the personal signals and the workspace
default so the viewer follows the Slack preference. It also returns
`languageSettings` — what is actually stored, since a resolved `en` cannot be
told from a deliberate one — which is what the viewer's Settings dialog shows
and what `PUT /api/docs/:workspaceId/language` writes back (personal for
anyone, workspace and content for a manager; see
`services/docs-editor/language-settings.ts` for the rules).

All three settings live on the encrypted `WorkspaceConfig` JSON blob; no
schema migration was needed.

## Picking the translator

`services/i18n/t.ts`. The rule is *whose eyes*, not *whose click*:

| Situation | Use |
|---|---|
| modal, ephemeral, `response_url`, rewriting the actor's own message | `tForRequest(context)` |
| a DM or card to someone else — a manager in a fan-out, the requester of an access request, a `chat.update` of a message previously sent to manager X | `await tForUser(workspaceId, recipientId, client)` — one per recipient inside the loop. Pass `client` when the recipient may never have been looked up (first contact) |
| a channel post with no single reader | `await tForWorkspace(workspaceId)` |
| a handler re-entered without a Bolt context (timers, synthetic payloads) | `tForReviewer` in `document-update/suggestions/shared.ts`, or `resolveLocaleForUserCached` |

`services/i18n/describe-error.ts` turns a thrown error into a sentence for
the reader: a `CHOIRError` with a catalog key renders translated with its
params; a plain `Error` passes its English message through. Never render
`error.message` directly into a translated frame.

## The catalog

`src/i18n/` (Slack side) and `web/src/i18n/` (viewer) are the same design:

- **English is the source of truth.** Feature files under
  `src/i18n/locales/en/*.ts` export flat `as const` objects; `en/index.ts`
  spreads them and `MessageKey` is derived from the result, so a typo in a
  key — or a plural call without `count` — is a `tsc` error caught by
  `pnpm verify`.
- **Other locales are partial overlays** (`ko/*.ts`, typed `LocaleCatalog`).
  `t` falls back to English *per key*, so a half-translated feature ships.
- **Keys** are `<feature>.<surface>.<element>[.<variant>]` and mirror the
  folder the strings came from (`qa.channelModal.title`,
  `docUpdate.extract.card.claimed`). A `.fallback` twin is the plain-text
  version for Slack's notification preview when the block carries mrkdwn.
- **Placeholders** are `{name}`, never `${}` — catalogs stay data.
- **Plurals** are `{ one: '…', other: '…' }` and require `{ count }`.
  Korean only has `other`. `Intl.PluralRules` picks the form.
- **Emoji prefixes live in the catalog.** URLs never do: store
  `'📍 {link} for context'` and pass a pre-formatted `<url|label>` whose
  label is itself a key. `*bold*` / `_italic_` may stay inline.
- **Slack length caps are enforced by the key's last segment**
  (`src/i18n/limits.ts`): `.title` ≤ 24 (modal titles — emoji count),
  `.button`/`.submit`/`.close` ≤ 75, `.option` ≤ 75, `.placeholder` ≤ 150,
  anything else ≤ 3000. Section *headers* are `.header`, not `.title`.
  `__tests__/i18n-catalog.test.ts` checks every locale against these caps,
  placeholder parity, balanced `*`/`_`, and that no `${` leaked in.

## Adding strings

1. Put the English in the feature's `en/<feature>.ts` (create one and add it
   to both `index.ts` files if the feature is new). Pick the suffix by what
   Slack will do with it, not by what it means.
2. Add the Korean to `ko/<feature>.ts`. 해요체, same voice as the LLM
   answers. Shorten the Korean if a modal title will not fit — never the
   English.
3. Call `t('…')` with the translator for the reader (table above).
4. Run `pnpm test -- i18n-catalog` and the feature's `*-i18n.test.ts`. The
   existing feature tests pin the English output to pre-migration fixtures
   under `__tests__/fixtures/`, so an accidental wording change fails loudly.

Do not add `i18next` or another runtime: the caps, the typed keys and the
per-key fallback are the whole point of the homegrown `t`.

## Adding a locale

`src/i18n/supported-locales.ts` — add the tag to `SUPPORTED_LOCALES`,
create `locales/<tag>/` mirroring `ko/`, add the option to the three App
Home selects (`appHome.language.option.*`) and the viewer's picker. The
catalog test will list every key the new locale is missing; an empty overlay
is a valid starting point.

## Content written into documents

`services/llm/content-language.ts` turns the workspace policy into one
prompt sentence for `knowledge-extractor`, `content-generator` and
`document-editor`. Under `follow-conversation` the rules are: extraction and
new sections follow the conversation/knowledge; a merge into an *existing*
section follows the existing content (so a Korean fact lands in an English
section as English, never mixed); image captions follow the document they
are committed into (`detectDocumentLanguage`, dominant script with code and
URLs ignored). File names stay English. Git commit messages stay English —
`[choir-auto]` is parsed.

`services/common/language.ts` is a Unicode-range guess, not a classifier:
`detectLanguage` (any Hangul → `ko`) is right for a Slack message,
`detectDocumentLanguage` (dominant script) for a whole file. It exists for
the fallback strings returned when a model call fails and for prompt hints;
UI strings never go through it.

## Retrieval

QMD's FTS5 table is tokenized with `porter unicode61`, which cannot be
changed from the SDK, so Korean document tokens are whitespace eojeol with
the particle attached. `services/retrieval/qmd-lex-search.ts` compensates on
the query side: Hangul tokens drop one trailing particle and a common verb
ending (never below two syllables), pass a Korean stopword list, and the
stemmed join leads the candidate ladder for Hangul queries.

Stemming cannot make `휴가` match `vacation`, so the vector leg carries the
cross-lingual work. When the question's language (`detectLanguage`) differs
from the repository's dominant language — sampled once per store with
`detectDocumentLanguage` over the first 25 section files, refreshed with the
index — `services/llm/query-translation.ts` translates the question with the
cheap `classification` model and adds it as a **second** `vec` query plus its
own `lex` candidates. The asker's own wording stays at index 0, which QMD
weights at 2.0 in its RRF fusion. Anonymization stays on (a question can name
a person), translations are cached per process (LRU, 200 entries, keyed by
workspace + query), the call has a 2s timeout, and every failure falls back
to the untranslated query list rather than failing the search.
`QMD_QUERY_TRANSLATION=false` turns the hook off.

The vector leg uses `embeddinggemma-300M`; `QMD_EMBED_MODEL` can point at a
multilingual model, but that requires a full re-embed and a CPU budget check
first. CHOIR now records the model each index was embedded with in
`<workspace>/state/qmd-index-v2.meta.json` and forces the re-embed itself when
the env var no longer matches, because a stale index used to degrade silently
to lexical search; a hybrid-search failure is now logged at `error` level with
that hint. `QMD_RERANK=true` enables QMD's `qwen3-reranker` (off by default —
it costs seconds per answer on CPU). See `docs/retrieval-migration.md`.

## Not translated on purpose

- LLM output (answers, extracted knowledge, topic labels) — content, not UI.
- Dashboard paraphrases (`services/dashboard/paraphrase.ts`) stay English:
  they are the clustering key. Topic *labels* shown to a reader are
  translated at relabel time into `qa_topics.labels_json` and picked by
  `?lang=`; `pnpm backfill:dashboard:labels --workspace <id>` fills in
  existing topics.
- Log lines, `throw new Error(...)` diagnostics that only reach operators,
  analytics labels, git commit messages, `action_id`/`block_id` values.
