# 지식 추출 재설계 — 멀티 계정 테스트 플랜 (Phase 1+2)

> Phase 3(체크박스 UI)는 아직 없음. 따라서 **수집된 후보가 곧바로 추출에 들어가며**, 추출 결과("Suggested Update" 메시지)를 보면 윈도우가 제대로 잡혔는지 바로 판단할 수 있다.

## 사전 준비

- **테스트 계정은 모두 CHOIR 등록 유저**여야 함(App Home에서 추가). **단 T5의 계정 C만 미등록.**
- 멘션은 **명확한 업데이트 요청**으로(예: "저장해줘 / 문서화해줘 / save this"). 그래야 `update_request`로 분류되어 추출 경로를 탐.
- **테스트 간 60초 이상 간격**(비-Marketplace rate limit: conversations.* 분당 1회).
- 갭/위치/cap 테스트는 아래 env로 빠르게 재현 (수정 후 재시작):

| env | 기본 | 테스트 팁 |
|---|---|---|
| `EXTRACTION_TIME_GAP_MINUTES` | 30 | 갭 테스트 시 **1**로 |
| `EXTRACTION_MAX_LOOKBACK_MINUTES` | 90 | |
| `EXTRACTION_MAX_CANDIDATE_MESSAGES` | 15 | cap 테스트 시 **3** 등으로 |
| `EXTRACTION_EARLY_REPLY_MAX` | 2 | early/late 경계 |
| `DEFAULT_TIMEZONE` | America/New_York | 유저 tz 없을 때만 사용 |

- 서버 로그에서 `gatherExtractionCandidates: ...`(safeSlackCall), rate-limit 경고를 함께 관찰.

## 시나리오

### T1 — 비스레드 단일 버스트 (기본 동작)
1. A: `다음 달부터 경비 보고서는 매월 5일까지 제출합니다.`
2. A 또는 B (30분 이내): `@CHOIR 이거 문서화해줘`

**기대:** 경비 정책을 **한국어**로 추출, "다음 달" → **절대 날짜(YYYY-MM-DD)**. 윈도우 = 두 메시지.
**검증 포인트:** 언어 일치(Phase 1), 시간 절대화, 비스레드 버스트 수집(Phase 2).

### T2 — 비스레드 갭 경계 (`EXTRACTION_TIME_GAP_MINUTES=1`)
1. B: `점심 뭐 먹지?` (무관)
2. ~70초 대기
3. A: `배포는 이제 prod 수동으로 합니다.`
4. A: `@CHOIR 저장해줘`

**기대:** **배포 정책만** 추출. 점심 잡담은 1분 갭으로 잘림.
**검증 포인트:** `keepLatestBurst` 갭 분절.

### T3 — 스레드 이른 멘션, 부모 이전 포함 ★핵심 기능
1. A (채널): `신규 입사자는 첫날 IT에서 노트북 받고, Okta 계정 만들고, 멘토 미팅 잡습니다.`
2. A (채널, 1과 30분 이내): `온보딩 메모` ← 이게 부모(thread parent)가 됨
3. B → "온보딩 메모"에 **스레드 답글**: `@CHOIR 위 온보딩 내용 문서화해줘` (1번째 답글 = 이른)

**기대:** 부모(2)엔 내용이 거의 없지만, **부모 이전(1)의 온보딩 사실이 윈도우에 포함**되어 추출됨.
**검증 포인트:** 이른 멘션 → 부모 이전 history fetch + anchor 연속성(Phase 2). "오래된/부모 이전 내용을 답글로 문서화"의 핵심.

### T4 — 스레드 늦은 멘션, 스레드만
1. A (채널): `코드리뷰 정책 정합시다.` ← 부모
2. 스레드 답글: B `2명 받자` → A `보안은 2명, 일반은 1명으로` → B `좋아요` → A `확정` (사람 답글 3개 → 늦은)
3. B (스레드 답글): `@CHOIR 이 스레드 정리해줘`

**기대:** **스레드 논의(보안 2명/일반 1명)만** 추출. 부모 이전은 안 가져옴.
**검증 포인트:** 위치 규칙(>2 → 늦은), 부모 이전 fetch 스킵.

### T5 — 동의 제외 (비-CHOIR 유저)
1. **미등록 계정 C**: `우리는 Zscaler VPN 씁니다.`
2. 등록 계정 A (같은 버스트, 30분 이내): `@CHOIR 위 내용 저장해줘`

**기대:** C의 메시지가 **제외**되어 documentable 내용 없음 → **보류**("documentable knowledge 못 찾음"). **의도된 동작**(동의 원칙).
**검증 포인트:** `filterMessagesByUsers` 제외. (C를 등록시키면 추출되는지 대조 테스트도 가능)

### T6 — 미합의 토론 보류
1. A: `리뷰어 2명으로 강제할까?` → B: `1명도 충분한데` → A: `음 글쎄`
2. A: `@CHOIR 이 논의 정리해줘`

**기대:** 결정 안 됨 → `No organizational knowledge found` 류 **보류**(쓰레기 정책 생성 안 함).
**검증 포인트:** v4 미합의 보류(Phase 1).

### T7 — 정정 (선택; 기존 문서 필요)
1. 문서에 어떤 값이 있는 상태에서 A: `@CHOIR [그 값] 관련 질문` → CHOIR가 문서 기반 답변
2. A: `@CHOIR 그거 [새 값]으로 바꿔서 저장해줘`

**기대:** **새 값으로 정정**된 문서. (컷 제거 후에도 qaContext "현재 문서 상태" 유지 확인)
**검증 포인트:** D9(컷 제거하되 qaContext 유지).

### T8 — cap (선택; `EXTRACTION_MAX_CANDIDATE_MESSAGES=3`)
1. A가 한 버스트로 메시지 6개 연속 게시 → `@CHOIR 저장`

**기대:** 최근 3개만 윈도우에 포함(로그/출력으로 확인).
**검증 포인트:** 총량 cap.

## 무엇을 보면 되나
- **추출 결과("Suggested Update")** 의 내용 = 수집된 윈도우의 반영. 기대한 사실이 들어왔는지/잡담이 빠졌는지로 판단.
- **언어/시간/보류** 는 결과 텍스트로 즉시 확인.
- **서버 로그**: `gatherExtractionCandidates:` 호출, rate-limit 경고, 분류 결과.
- 막히면 함께 디버그: 어떤 메시지가 들어오고 빠졌는지 로그를 같이 보면 됨.
