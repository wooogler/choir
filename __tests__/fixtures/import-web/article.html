Deployment handbook

This handbook describes how a service reaches production at Example Corp. It is written for engineers who already have a service running locally and now need to put it in front of real traffic. Every step below has been run by a person on the platform team at least once a week for the past year, so the surprises that remain are mostly the ones your own service brings with it. Read the whole page once before you start; the order of the steps matters more than any individual command does.

Before you start

Make sure you can reach the staging cluster and that your service builds from a clean checkout. If either of those is not true, fix it first — every failure mode further down looks identical to a broken build, and you will spend an afternoon reading logs that were never going to tell you anything useful.

  • A green build on the default branch
  • Access to the cluster
    • Staging, for the rehearsal
    • Production, for the real thing
  • An on-call rotation that knows you are shipping

Configuration

Configuration lives in the repository, not in the cluster. The deploy script reads it at build time, so a change to a value requires a new build and a new rollout. See the configuration reference for the full list, and the status page when something looks wrong. 

export const config = {
  region: 'ap-northeast-2',
  replicas: 3,
};

Rollback

SymptomAction
Error rate above 1%Roll back immediately
Latency above 500msHold the stage and page the owner

Rolling back is not a failure. Leaving a bad rollout in place because you hoped it would settle is.

Run deploy rollback and then tell the channel. The command is idempotent, so running it twice is safe, and it is the only action in this document that never needs approval. Need help?
